Opening

After this session

  1. Explain what a sequence diagram is for, and what it leaves out.
  2. Choose the participants for one scenario.
  3. Tell an actor, an object, a lifeline, and an execution apart.
  4. Read time from top to bottom.
  5. Draw synchronous, asynchronous, reply, self, create, and delete messages.

Purpose

Collaboration over time

A sequence diagram shows how participants collaborate to realize one scenario.

It answers who takes part, which messages they exchange, the order of those messages, and when someone is actually executing.

Time runs from top to bottom. Left to right is layout.

Purpose

Leave these to another diagram

  • Static class structure
  • A database schema
  • A complete state machine
  • Every data transformation
  • Every scenario in one frame
  • Precise timing, unless you add a constraint

Use a class diagram for structure, a state machine for lifecycle, and an activity diagram for workflow.

Participants

A participant is whoever takes part

  • An external actor
  • A specific object
  • An instance of a class
  • A subsystem or a service
  • A database, when that view needs it
  • An external system

An actor is an external role. The others collaborate inside the boundary you chose. Label each lifeline at that same level.

Participants

Left to right is not time

  1. 1Initiating actor
  2. 2Boundary or interface
  3. 3Control or application service
  4. 4Entity, repository, or external service

That order is easier to read. A message farther right is not a later message.

Lifelines

A head, then a dashed line

The dashed line is presence during this interaction. Time moves down the line.

Lifelines

Present is not the same as executing

Lifeline

The participant exists, or takes part, through this stretch of the scenario.

Execution specification

The thin bar. A period in which that participant is performing behavior.

Do not stretch one bar down the whole lifeline. That confuses existence with work.

A verb phrase, or an operation with its arguments. The receiver is the participant who must perform it.

Messages

Higher happens first

insertCard, then verifyCard, then cardValid, then requestPIN. Down the page, not across it.

Messages

The sender waits

A synchronous message is a solid line with a filled arrowhead.

The sender does not continue that thread until the invoked behavior finishes. A service waiting on a query is the usual case.

The filled head is the distinction. A solid line by itself does not make the call synchronous.

Messages

A reply is optional

A reply is a dashed line with an open arrowhead. It returns control, a value, or a status from an earlier call.

Draw it when the result matters: a returned value, an error, or a completion the reader would otherwise miss.

UML does not require a reply on every synchronous call. Omit the ones that only add clutter.

Messages

A PIN is a new message

requestPIN asks. enterPIN(pin) is a solid message from the customer. A dashed reply would say the ATM returned a value.

Messages

The sender continues

An asynchronous message is a solid line with an open arrowhead. The sender does not wait for the receiver to finish.

Publishing an event, writing to a queue, or a fire-and-forget notification.

A network hop does not make a call asynchronous. A remote HTTP request can still be synchronous for the caller.

Messages

A participant calls itself

A self message is the participant invoking its own behavior.

Show the internal step when the design discussion needs it, such as checking the amount format before asking the bank.

Leave private helpers off the diagram.

Messages

Lifetimes that start and stop

A dashed open arrow into the new head. The lifetime begins here. The label is name : Type.

close() is an ordinary call. The cross at the end of the lifeline ends that instance.

Draw creation and destruction only when the scenario cares about the lifetime.

Execution

The bar is the work

ATM stays active across the bank call. Bank Server is active only while it validates the card. The customer has no bar.

Execution

Three rules for the bar

  • The bar is a period of behavior, including time spent in a nested call. It does not mean the object is alive.
  • An actor may have a bar when that active participation matters. Omitting actor bars is a readability choice, not a UML rule.
  • Do not wrap every message on a lifeline in one bar. Line the bar up with the control that is actually running.

Fragments

A guard is a testable condition

Write thisNot this
[card valid][okay]
[PIN invalid][error]
[availableBalance >= amount][normal]
[attempts < 3][else], when you can name the condition

Square brackets. Mutually understandable, concise, and taken from the scenario. Operands should not overlap unless you mean a nondeterministic choice.

Fragments

The operator names the control

alt — mutually exclusive alternatives
opt — one optional branch
loop — repetition, with a bound
par — operands that may run together

Also available, and not the focus today: break aborts the enclosing interaction, critical marks an atomic region, and ref points at another interaction.

Fragments

One of these, not both

[card valid] and [card invalid] cannot both be true. A valid card asks for a PIN. An invalid card comes back out.

Fragments

Only when the guard is true

opt has a single operand. There is no else branch.

Use it when the behavior is optional and the alternative is simply to continue.

A receipt is not an alternative to the withdrawal. It is an extra step when the customer asked for one.

Fragments

Say how the repetition stops

The loop runs while the PIN is invalid and attempts remain. [attempts < 3], [for each selected account], and [while payment pending] are the same kind of bound. A loop with no bound is unfinished.

Fragments

Only when they really run together

Audit and notification may proceed concurrently. Both arrows are open, so the bank does not wait. par is not a box for steps that merely belong together.

ATM

Build Withdraw Cash in five passes

  1. 1Write the scenario: success, plus invalid card, invalid PIN, and insufficient funds.
  2. 2Keep Customer, ATM, Bank Server, and Bank Account. Drop anyone the scenario does not need.
  3. 3Validate the card, with an alt and two explicit guards.
  4. 4Validate the PIN the same way.
  5. 5Check funds, debit or decline, dispense or explain, then return the card.

ATM

A valid PIN asks for an amount

This simplified path ejects the card on the first bad PIN. A production ATM would loop the attempts instead of stopping here.

ATM

Debit and dispense, or decline

ejectCard() sits outside the alt, so the card comes back whether the withdrawal is approved or declined. This is the build step, not the nested model yet.

The card check contains the rest

[card invalid] ends here. [card valid] leaves the ATM and the bank active: the PIN check on the next slide is inside this branch, not a new scenario.

ATM · the nested model

Still inside the valid card

ATM · the nested model

Inside the valid PIN

[sufficient funds] debits and dispenses. [insufficient funds] declines. ejectCard() follows either outcome, then the ATM bar closes.

ATM

One interaction, read in order

Read the previous three slides as one interaction. The PIN check sits inside [card valid], and the withdrawal sits inside [PIN valid].

  1. The customer inserts a card.
  2. The ATM asks the bank to validate it.
  3. An invalid card is rejected.
  4. A valid card leads to PIN entry.
  5. An invalid PIN ends this simplified scenario.
  6. A valid PIN leads to the amount.
  7. The bank checks the account.
  8. Enough funds: debit, then dispense cash.
  9. Not enough funds: the withdrawal is declined.
  10. The ATM returns the card before the interaction ends.

ATM

Do not force every variant into one frame

  • Three PIN attempts
  • A retained card
  • Withdrawal limits
  • Whether the ATM has the cash
  • Account locks and fees
  • Audit logging
  • Timeout and cancellation
  • Partial hardware failure
  • Debit succeeded, cash did not
  • The compensation for that failure

When the alternatives get hard to read, draw another scenario. Reference it instead of nesting it here.

Levels

The system is one black box

Use this to find system events and actor interaction. cashAndCard is a reply because it returns the outcome. Do not open the box yet.

Levels

Open the box to assign work

The controller finds the account, authorizes the amount itself, and tells the dispenser to pay out. This is a design view of one step, not a second copy of the black box.

Levels

Boundary, control, entity

Boundary faces the actor. Control coordinates the scenario. Entity holds domain information and behavior. A heuristic, useful when it clarifies responsibility, never a required stereotype.

Review

Mistakes that change the meaning

  1. 1One diagram for the whole system. Split by scenario, variant, or service.
  2. 2A class name where the view needs an instance. Prefer atm : ATM, and stay consistent.
  3. 3A dashed reply for every thing the user types. User input is usually a new message.
  4. 4A reply on every call. Keep a reply when the value or the completion teaches something.
  5. 5An alt with no guards. Each operand needs the condition that selects it.
  6. 6alt used for a single optional step. That is opt.

Review

Mistakes that change the meaning

  1. 7One bar for the whole lifeline. Existence and execution are different marks.
  2. 8Later messages drawn farther right. Time is downward.
  3. 9A business actor, a subsystem, a private helper, and a database table in one frame, with no reason.
  4. 10A happy path only. Model the important failures, or give them their own diagram.
  5. 11A message with no responsible receiver. Someone has to perform the behavior.
  6. 12Control logic written only in a note. Guards and fragments carry the order. Notes explain.

Review

Before you call it done

Scenario

One title. A known outcome. One abstraction level. Important alternatives present or referenced.

Participants

Each one is needed. Actors are external. Labels agree. The order is for reading.

Messages

Top to bottom. Verb phrases. Sync and async chosen on purpose. Replies only when they help. Self messages stay few.

Fragments

alt operands exclude each other. opt is one branch. loop states a bound. par is real concurrency. Guards are testable.

Execution and life

Bars match the work. Create and delete appear when the lifetime matters. A dashed line is not a bar.

Readability

Readable on a slide. Few crossing lines. No implementation clutter. Notes do not replace the notation.

Ask the room

Questions that keep the model honest

  • What single scenario does this diagram realize?
  • Which participant owns this responsibility?
  • Does the sender wait for completion?
  • Is this dashed arrow really a returned result?
  • What exact Boolean condition selects this operand?
  • Does this behavior repeat, stay optional, or run in parallel?
  • Is the lifeline alive, or actively executing?
  • Are we looking at a black box, or at internal design?
  • Would a separate diagram make this alternative clearer?

Practice

What is wrong with each claim?

  1. A reply message is used for every user input.
  2. Later messages are placed farther to the right.
  3. One activation bar covers the participant’s whole lifeline.
  4. An alt fragment has no guards.
  5. One diagram shows Customer, ATM System, WithdrawalController, a private helper, and a database table.

Practice

What is wrong with each claim?

  1. User input is a new message, unless that arrow truly returns a value.
  2. Time runs downward. Horizontal position is layout.
  3. The lifeline is existence. The bar is active execution. They have been collapsed into one mark.
  4. The conditions that select each operand are missing.
  5. Black box, design, source code, and persistence are mixed, and the diagram never says which view it is.

The words, in one place

Actor. An external role in the interaction.

Participant. An actor, object, role, service, or subsystem.

Lifeline. That participant’s presence over time.

Message. Communication between lifelines.

Synchronous. The sender waits for completion.

Asynchronous. The sender does not wait.

Reply. A returned value, or return of control.

Self message. A participant invoking its own behavior.

Create. A message that begins a lifetime.

Delete. A message that ends a lifetime.

Execution specification. A period of active behavior.

Guard. A Boolean condition on an operand.

Combined fragment. A frame for alt, opt, loop, par, and the rest.

System sequence. Actors talking to the system as one black box.

Close

Twelve things to keep

  1. A sequence diagram is an ordered interaction for one scenario.
  2. Time runs from top to bottom.
  3. A lifeline is presence, not continuous execution.
  4. The bar shows when behavior is executing.
  5. The arrowhead and the line together choose the message sort.
  6. A reply is optional, and it should add information.
  7. User input is not automatically a reply.
  8. A guard is a condition you could test.
  9. alt, opt, loop, and par are different kinds of control.
  10. A system sequence and a design sequence are different levels.
  11. One focused scenario beats one enormous diagram.
  12. Every message assigns a responsibility.
