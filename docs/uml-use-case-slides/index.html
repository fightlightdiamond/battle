Purpose

A map of external behavior

A Use Case Diagram shows the system under discussion, who is outside it, the goals they achieve, and how those pieces are related.

It helps when an idea is clear to its author and unclear to everyone else.

Purpose

Four questions

  1. 1System — what are we modeling?
  2. 2Actors — who or what interacts with it?
  3. 3Use cases — what goals do they achieve?
  4. 4Relationships — how are they connected?

Purpose

Leave these off the diagram

  • Step-by-step execution order
  • Algorithms and internal design
  • Classes, tables, and screens
  • Every error and alternative flow

Those belong in a Use Case Specification, or in an activity, sequence, or class diagram.

Can be

  • A person

Who starts, and who supports

Actor

Ask before you add one

  • Who initiates a goal through the system?
  • Who receives value from it?
  • Which external systems or devices exchange information with it?
  • Who administers or supports it?

Use case

A goal the system provides

Drawn as an ellipse inside the boundary.

  • Start the name with a verb.
  • Say the result, not the screen.
  • Stay specific, and keep the vocabulary consistent.

Use case

Not every step is a use case

Only a result someone outside the system can recognize belongs on the diagram. The same story, “move money,” has three different levels.

Actor goal

Transfer Funds

The customer opens the app to move money. When it finishes, they know the goal is done. Draw this as a primary use case: an ellipse inside the system boundary.

Shared behavior

Verify Sufficient Funds

The customer does not open the app just to check that enough money is there. Transfer Funds and Make Payment both need this step, so extract it and connect it with «include».

Not a use case

Read an internal variable

Reading a field, calling a private function, or querying the database is an implementation detail. The customer never sees it. Record it in the specification or the code, not as an ellipse.

Where an ellipse sits is not the order it runs. Log In drawn above Transfer Funds is only to keep the page readable. If login must happen first, write that precondition in the use case specification.

Relationships

Four kinds of line

Association

Solid line, no arrowhead. The actor participates.

«include»

Dashed arrow, from the base to the included behavior.

«extend»

Dashed arrow, from the extension back to the base.

Generalization

Solid line. The hollow triangle sits on the general element.

Association

Only a real participation

Does this actor actually communicate with this use case? If not, do not draw the line.

«include»

The base pulls in required behavior

Use it for behavior that is required, shared, or worth extracting so it is not copied.

Arrow: base use case → included use case

«include»

Log In includes Verify Password

The dashed arrow points at the behavior being included.

«include»

One included use case, two bases

Transfer Funds and Make Payment both include Verify Sufficient Funds. Do not draw that check twice.

«extend»

Added only when a condition holds

The base use case must still make sense without the extension.

Arrow: extending use case → base use case

«extend»

A bad password extends Log In

The error is not shown on every attempt. The arrow points at the use case being extended.

«include» and «extend»

Same base, two different arrows

Include points away from Log In. Extend points back at Log In.

Check

Are we extracting required behavior, or adding something the base does not need?

“Include always, extend sometimes” is only a hint. Ask about the base first.

Generalization

A specialized element is a kind of the general one

It inherits the relevant behavior and relationships, and may add its own.

Solid line. Hollow triangle points at the general element.

Generalization

Two ways to make a payment

The hollow triangles sit on Make Payment. Pay from Checking and Pay from Savings inherit its associations.

Generalization

New and returning customers are customers

The triangles point at Customer. The specialized actors inherit the association with Make Payment.

Extension point

Name the place where behavior may be inserted

Add an extension point only when the insertion location helps the reader.

Building the diagram

Eight passes, in this order

  1. 1. Name the system and draw the boundary.
  2. 2. Place Customer and Bank outside it.
  3. 3. Add the four customer goals inside.
  4. 4. Associate actors only where they participate.
  5. 5. Include Verify Password and Verify Sufficient Funds.
  6. 6. Extend Log In with Display Login Error.
  7. 7. Specialize Make Payment into checking and savings.
  8. 8. Remove crossings, UI details, and unused actors.

Banking App

The whole model

Banking App

Read the lines, not the layout

  • Customer starts the business goals. Bank supports balance and money movement.
  • Log In includes password verification.
  • A login error extends Log In only when the password is incorrect.
  • Transfer and payment both include the funds check.
  • Checking and savings payments specialize Make Payment.

Review

Mistakes that show up early

  • Naming an actor after a person, or placing an actor inside the boundary.
  • Using a noun, or a screen, as a use case name.
  • Treating vertical position as the order of execution.
  • Giving every error its own «extend», or connecting every actor to every use case.
  • Drawing a database inside the scope as an actor.

Review

Where the marker sits

«include» — base → included
«extend» — extending → base
Generalization — specialized → general, hollow triangle on the general element
Association — solid line, no arrowhead

Review

Before you keep the diagram

  • The boundary matches the scope you mean.
  • Actor names are roles. Each one participates.
  • Use case names are verb phrases at one level.
  • «include» points at the included use case.
  • «extend» points at a base that still stands alone.
  • Generalization is a true general–specialized pair.
  • A reader can see the goals without a long explanation.
  • Flow detail has moved to the specification.

Close

Keep these ten

  1. The diagram is the external view of goals and interactions.
  2. The system boundary is the scope decision.
  3. An actor is a role, not a named person.
  4. A use case name is a verb phrase for a goal.
  5. Association means participation, and has no arrowhead.
  6. «include» points from the base to the included use case.
  7. «extend» points from the extension to the base.
  8. Generalization points from the specialized element to the general one.
  9. The diagram stays simple and does not replace the specification.
  10. When it gets crowded, split it or move detail elsewhere.

Ask the room

Questions that keep the model honest

  • What goal is the actor trying to achieve?
  • Is this responsibility inside the boundary or outside it?
  • Does this name express a goal, or is it only a noun?
  • Is the base use case meaningful without the extension?
  • Should this arrow point at the included behavior or at the base?
  • Does this detail belong on the diagram or in the specification?
